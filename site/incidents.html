A finding is worth nothing where nobody looks

A governance tool that prints to a terminal is a governance tool that gets run once. Every finding is written back into DataHub as an incident on the entity it concerns, so it appears next to the table in the catalog a data team already opens, and shows up as a health signal on any lineage walk that passes through.

  • raised 9
  • state all active
  • on 2 feature tables
  • write gate --raise
writing

Nothing is written without asking for it

The default is a dry run that prints exactly what it would file. Priority comes from the basis the regime assigns, not from a guess: a prohibited basis is critical, a conditional one is high, and a column merely in scope for examination is low. 

python tools/incident.py --model workforce-classifier --policy employment_us --raise

What DataHub holds now

Read through the GraphQL API as an ordinary consumer would, not from any state file of ours. If these were not really in DataHub this query would return zero. 

POST /api/graphql  { dataset(urn: "...income_features") { incidents { total incidents { title priority } } } }
income_features 6
  HIGH     | race (Some other race) became easier to rebuild from income-classifier
  HIGH     | race (Asian alone) became easier to rebuild from income-classifier
  HIGH     | race (Black alone) became easier to rebuild from income-classifier
  CRITICAL | race_code reaches income-classifier_3
  CRITICAL | marital_status_code reaches income-classifier_3
  HIGH     | age reaches income-classifier_3

POST /api/graphql  { dataset(urn: "...workforce_features") { incidents { ... } } }
workforce_features 3
  HIGH     | disability (With a disability) became easier to rebuild from workforce-classifier
  LOW      | marital_status_code reaches workforce-classifier_3
  CRITICAL | age reaches workforce-classifier_3

All nine are ACTIVE. The three race findings are one per comparison group, each measured against the reference group separately, which is how adverse impact analysis compares and why they are three incidents rather than one.

the finding that changed the design

Incidents will not attach to a model

The original plan was to raise the incident on the deployed model, which is where the consequence lives. DataHub v1.5 refuses an mlModel urn at the entity layer. Only datasets, data jobs, data flows, dashboards and charts carry the aspect. Probed live, and it creates nothing rather than creating something broken. 

raiseIncident(input: { resourceUrn: "urn:li:mlModel:(urn:li:dataPlatform:mlflow,workforce-classifier_3,PROD)" ... })
"urn:li:mlModel:(urn:li:dataPlatform:mlflow,workforce-classifier_3,PROD) is not a valid destination"

So they are filed on the feature table instead, with the model named in the title and the body. That turned out to be the better home rather than a consolation: the feature table is where the column entered and where a fix is made, and the model is reachable from it in one hop. The project's own definition of done said "an incident on a real MLModel", and that was not achievable, so it was corrected rather than quietly reworded.

This is one of the contributions being written up for the DataHub project. Two smaller notes found the same way: the server blocks multi-type introspection, and there is no delete mutation for an incident, so a test that raises one leaves it.

why it matters downstream

The findings come back on their own

Because they are real entities, a later lineage walk sees them without being told. The health block below arrived inside an ordinary get_lineage response, which means an agent investigating something else finds the earlier finding on the way past. 

"health": [
  {
    "type": "INCIDENTS",
    "status": "FAIL",
    "message": "3 active incidents",
    "causes": ["ACTIVE_INCIDENTS"]
  }
]
